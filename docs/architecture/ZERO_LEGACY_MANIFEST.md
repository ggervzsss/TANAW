# TANAW Zero-Legacy Manifest

- Status: **Open — implementation inventory and removal gate**
- Owner: **Program coordinator**
- Independent reviewer: **Unassigned**
- Target contract: **2**

This is the authoritative hard-cutover manifest required by
`TANAW_REPORT_WORKFLOW_IMPLEMENTATION_PLAN.md`. It is intentionally populated
with every superseded object or behavior already known from the review. Agents
MUST add exact tables, columns, indexes, views, routes, DTOs, event types, source
symbols, local stores, jobs, flags, adapters, generated artifacts, and deployment
objects as they discover or create them.

Rows are never deleted to make the list appear complete. They advance to
`verified` with linked evidence and independent review.

## Classification and status

| Classification           | Meaning                                                                                                               |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `retain_as_target`       | The object is explicitly part of the target design; prove that only its approved responsibility remains               |
| `transform_then_drop`    | Reconcile required data/behavior into target objects, then physically remove the legacy object                        |
| `drop_without_migration` | The object is invalid, fabricated, duplicated, generated, or has no legitimate state to preserve                      |
| `migration_only_remove`  | Temporary adapter/comparison/checkpoint object allowed only in development or rehearsal and removed before acceptance |

Allowed row status is `open`, `in_progress`, `transformed`, `removed`, or
`verified`. `verified` requires both transformation proof (or an approved reason
none is required) and absence/target proof. An independent reviewer records name,
date, build/migration hash, and evidence location in the row or linked cutover
record.

## Required proof record

For each row moving to `verified`, attach or link:

- exact object/symbol names and final classification;
- migration revision/build/release hash;
- input counts, normalized totals/hashes, exceptions, and reviewer disposition;
- the transformation command and output location;
- the absence query/search command and unedited output;
- targeted and full quality/E2E command results;
- reviewer, UTC verification time, and signature/approval reference.

Minimum database absence evidence includes PostgreSQL catalog queries for tables,
columns, views, indexes, triggers, constraints, and functions, plus SQLite
`sqlite_master`, `table_info`, index, trigger, and filesystem checks. A missing
ORM model is not proof that a table was dropped.

Minimum code absence evidence includes repository `rg`, OpenAPI and route/event
registry diffs, generated-client inspection, production build/package search,
environment/deployment configuration search, and a target-only end-to-end run.
A passing unit test is not proof that a compatibility branch is absent.
